One thread, with threads where they earn it

Family Assistant opens on a single Home stream, like a Telegram DM with the assistant. Quick questions and answers stay inline. Work that is long-running, multi-step, or that the user will come back to gets spun off into a thread. In Home, a thread is one live card. Its detail lives behind the card. When it finishes, its outcome is echoed back into Home, so Home reads as the full story at headline level.

Home replaces today's chat list as the landing screen. The list is now the thread switcher, reached from the top-right button, whose badge counts threads waiting on you. Every thread card in Home, and every row in the switcher, pushes into the thread.

How it behaves

When does something become a thread?

  • The assistant decides, and says so. It starts a thread when the work will outlive the turn: delegations, browser runs, research, anything that waits on someone else, or a multi-turn project like "plan the Japan trip". The reply in Home says "I've started a thread", so it's never a surprise.
  • One-off questions stay in Home. Lookups, quick edits, reminders, small talk.
  • The user can always override. On any message, "Continue in a thread" carries the context with it, and "Move to thread…" files the whole turn into an existing thread. On web, ⌘⇧↵ sends as a new thread, and the switcher has "New thread".
  • Two parallel jobs means two threads. Each thread is its own conversation, and the browser scope is already keyed per conversation, so two jobs never share a tab.

What Home shows

  • One live card per thread, updated in place, never a stream of progress messages.
  • States: working (an active turn, delegation or worker) · failed (a run or turn ended in a terminal failure, derived by code) · done · waiting on you (anything else: the next move is yours). The unread count is separate and per person, so one person reading a thread doesn't clear another's badge.
  • Answering a thread always reaches the thread. Quick replies on a card (Gas / Heat pump, Hold Jetstar) go into the thread, where its profile, tools and browser tab are. Home's assistant never acts on a thread's behalf.
  • When a thread is done, its final message is echoed into Home, the way Slack's "also send to channel" works. A thread that ends on a question is waiting, not done. A done thread reopens when something new arrives in it, such as a reminder it set, and it echoes again when it finishes.
  • A card that has scrolled out of view doesn't re-post. The switcher badge, the sidebar and push notifications carry "waiting on you".

Navigation

  • iOS: Home is the landing screen. ☷ opens the thread switcher, which replaces today's chat list and is grouped as Waiting on you / Working / Done today / Earlier. Tapping a card pushes into the thread, and Back returns to the same place in Home.
  • Web: the sidebar is Home plus threads grouped by state. A thread opens in a right panel so Home stays readable, which is the fix Grok Bot users asked for. ⤢ expands it, and on narrow windows the panel takes over the screen.
  • Telegram: the private chat is the Telegram Home. Thread cards are messages edited in place, and replying to a card routes into its thread. Other reply chains work as they do today.
  • Voice: a voice session started from the app belongs to that app's Home. A job that becomes a thread is announced, and its card appears in Home.

What the assistant sees

  • Home sees its own history plus each thread's facts: the title written when the thread was created, its state, and the echoed final message. It never sees the generated summary, which carries no taint.
  • A thread started by the assistant carries what a delegation does today: the request it was given, never the anchor turn or the Home transcript. The "Started from" quote is display-only. Only the user's "Continue in a thread" brings earlier Home turns along, and never into coder or media analyst. Copies keep their taint. A thread doesn't see its siblings.
  • Each thread keeps its own profile and tier. Home stays on the default profile, and a tier picked in Home applies to that turn only.

Model: a thread is a conversation with a parent

  • Home is one designated conversation per user per surface. Web and iOS share one Home, and Telegram's private chat is the Telegram Home. A thread is an ordinary conversation plus a link record holding the parent Home, the anchor turn and the state. Legacy conversations are neither: they sit under "Earlier" and are never migrated.
  • Why not surface subconversations? They're a delegate's private working history: the request text is written by a model, they allow one active run each, and they're excluded from /messages, summaries and the list by design. Meanwhile streams and resume, active turns, cancel/steer, activity pings, ownership, share links, the sticky tier, profile adoption, summaries and memory review are all keyed per conversation already, so threads get all of that unchanged. Subconversations stay as they are, inside a thread's conversation.
  • Starting a thread is a delegation that delivers differently. It runs on the existing delegation_runs machinery, targeting the thread's own conversation, with no wake back to Home. It's admitted by the target profile's delegation policy and carries delegation taint.
  • Everything that crosses between conversations goes through one chokepoint. That covers the seed, "Continue in a thread", a moved turn and the echo. It applies three rules. Rows keep their taint and are re-stamped to the destination's profile. Coder and media analyst accept request text only, and moves into them are refused. Only text the user typed is stored as a user row, so an assistant-written request never counts as the user's words for memory.
  • The echo replaces the wake. Finishing a thread copies its final message into Home. Home's assistant isn't run again to restate it.
  • Telegram needs a per-conversation turn slot. Otherwise a Home message sent during a thread turn would steer that turn.

Decisions

  • The assistant starts threads on its own from day one.
  • Done threads reopen on later events (the day the plumber comes is the same thread).
  • Card quick replies come only from explicit questions the thread asks. A general suggested-replies mechanism may come later.
